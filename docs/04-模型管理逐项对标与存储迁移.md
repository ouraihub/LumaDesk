## 3. 为什么此前使用 JSON，以及问题所在

此前按小规模单进程快照设置实现，复用了 save_versioned/atomic_write，优点是写入失败保留旧文件、无迁移表。这个取舍没有满足逐项对齐的目标：多个实体缺少数据库外键/唯一性约束，改一个字段需重新编码整份目录，独立密钥更新和后续高级模型元数据难以明确事务边界。

问题不是 JSON 一定不安全，也不是用了 SQLite 就自动实现功能。现在已有SQLite依赖却未接入产品，是架构差异。不能把model-settings.json全文存成数据库单行来声称模型目录已关系化。

## 4. SQLite 迁移设计

### 模型目录数据库

优先按参考实体分层：providers、endpoints、models、endpoint_keys、store_meta。模型复合主键(endpoint_id,model_id)，线路归属provider，密钥归属endpoint；启用、顺序、选中项、预设初始化状态有明确字段。模型高级结构（推理配置/分档价格）可使用校验过的JSON列，与参考方式一致。密钥使用BLOB保存原系统密文，不解密后迁移。

- 用既有 SQLite 迁移器建立/升级schema；明确foreign_keys、事务、唯一性、CHECK和级联。
- 服务商编辑事务仅更新该服务商，密钥保存/删除各自独立，启用用UPDATE，不提交地址草稿。
- 成功提交后更新saved快照和选择器；失败回滚，UI留草稿；网络运行取不可变连接快照。
- 不引入ORM、通用仓储接口或多种存储后端。

### 旧数据一次性迁移

1. 数据目录现有内核锁保证宿主写入者唯一。
2. 开库后先检查迁移标记；若尚未导入，完整读取并验证旧JSON版本/内容，保留原文件。
3. 在同一事务导入全部实体、稳定ID、顺序、首选项、密文字节及预设标记，并写入导入完成标记。
4. 事务失败不写完成标记、不更新内存；重启可安全重试。旧JSON不删除、不作为之后的第二数据源。
5. 数据库已初始化后，以数据库为唯一来源；数据库空目录也不能重新导入旧JSON复活已删除数据。
6. 新版本schema拒绝旧程序写入；损坏/不可写明确报错，不静默回退到JSON或新空库。
7. 用户备份/恢复须明确数据库文件与可能的WAL状态，不能仅复制一个未检查的活跃文件。

### 应用其它数据的边界

用户已明确选择“全部现有持久化数据”。本次同时切换模型目录、聊天会话、搜索设置和外观偏好：providers.db、chat.db、settings.db（搜索实体与外观prefs）。各领域旧JSON在同库事务中完成导入与标记，保留旧文件备份但不再读取或双写。保留现有数据目录锁；各库失败明确报错，不能回退空数据。跨领域不做无依据的全局事务，启动前的导入只影响对应领域且可幂等重试。

实施约定：所有数据库沿用默认回滚日志模式，不启用WAL。正常关闭程序后备份整个data目录（providers.db、chat.db、settings.db及已有日志/旧JSON），不能在运行时只复制单个db文件当作一致备份。旧JSON导入保留原字节，不把密钥解密再写入；数据库初始化标记与领域数据在同一事务提交。启动部分领域导入成功、其它领域失败时不会混用JSON继续启动，下次只重试未完成领域。
