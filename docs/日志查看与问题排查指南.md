# LumaDesk 日志查看与问题排查指南

开发与审查遵守[日志与异常规范](日志与异常规范.md)；本文只说明排查操作。

## 1. 先理解日志级别

默认级别是 `INFO`，只显示关键操作入口和最终结果；正常使用不需要长期打开 `DEBUG`。

| 级别 | 用途 |
|---|---|
| `ERROR` | 需要处理的最终失败 |
| `WARN` | 下层失败、超时、降级和可恢复问题 |
| `INFO` | 用户动作的开始、成功结束和取消 |
| `DEBUG` | HTTP、存储、模型请求等下层边界 |
| `TRACE` | 最底层协议和细节，通常只在开发排查时使用 |

排查步骤：

1. 打开「设置 → 后台日志」。
2. 把「记录级别」切到 `DEBUG`。
3. **重新执行一次出问题的操作**。
4. 在日志页按 TraceId 搜索，或点击已有行的 TraceId 标签。
5. 展开「诊断详情」查看源码位置和原始日志行。

切换级别不会补录历史日志。切换前被 INFO 过滤掉的 DEBUG 行不会出现在旧 TraceId 中；页面会提示“请重新执行操作”。切换后的提示会显示在日志页顶部。

## 2. 如何定位到源码

生命周期日志包含：

```text
ME:settings.mcp.load|SourceFile:src/mcp_settings.rs|SourceLine:38|EV:ENTRY
```

- `ME`：稳定的业务操作名，不一定等于 Rust 函数名；
- `SourceFile`：仓库相对源码路径；外部依赖无法归属时仅保留安全文件定位；
- `SourceLine`：创建该 root 或下层 operation 的源码行；
- `Layer`：`ui`、`service`、`repository`、`external` 等边界；
- `EV`：`ENTRY`、`EXIT`、`ERROR`、`CANCEL`、`TIMEOUT` 或 `UNFINISHED`；
- `RT`：操作实际耗时，单位毫秒；
- `Error` / `Reason` / `Limit`：稳定错误码、取消原因或配置的超时时限。

日志列表默认隐藏源码段，展开「诊断详情」后显示 `SourceFile:SourceLine`。这避免普通浏览被路径和字段淹没，同时保留开发定位能力。

## 3. 用 TraceId 还原完整链路

一次失败通常应看到：

```text
入口 INFO  settings.mcp.save       ENTRY
下层 DEBUG settings.mcp.store.save ENTRY
下层 WARN  settings.mcp.store.save ERROR
入口 ERROR settings.mcp.save       ERROR
```

根操作通常只记录一条 `ERROR`；下层失败记录为 `WARN`。用户取消不是错误，会显示 `CANCEL`。超时显示 `TIMEOUT` 和 `Limit`。

使用「复制诊断 ID」复制完整 TraceId，再粘贴到日志页搜索框。不要只复制页面显示的前 8 位。

## 4. 常见误解

- 看到 `INFO ENTRY/EXIT` 不代表没有下层日志；可能是操作发生时级别仍为 INFO。
- 切到 DEBUG 后必须重新操作；旧链路不会改变。
- `Target` 是普通事件的来源模块；生命周期行优先看 `ME`、`Layer`、`SourceFile` 和 `SourceLine`。
- 日志不会记录 API key、密码、Authorization、完整用户消息、模型回答或上游错误正文。
- 上游 request-id 与端点使用诊断哈希，不再保存原始 URL 路径或响应头。供应商排查应使用宿主 TraceId 与脱敏关联信息，不期待从日志恢复原始正文。
- Rust panic 单独同步写入 ERROR。其后的 UNFINISHED 表示操作被程序错误打断，不是正常取消；不要在正式资料上主动制造崩溃。

## 5. 提交问题时附带什么

建议提供：

1. 完整 TraceId；
2. 发生时间；
3. 操作名称或页面名称；
4. 是否在 DEBUG 下重新执行；
5. 展开的诊断详情中的 `SourceFile:SourceLine`、`EV`、`Error`、`Reason` 或 `Limit`。

不要直接粘贴包含敏感信息的完整日志文件。优先复制筛选后的链路，并先检查是否包含个人数据。
